# Mini Redis

Redis의 핵심 자료구조를 밑바닥부터 직접 구현한 CLI 기반 인메모리 Key-Value 저장소입니다.

## 왜 Redis는 빠른가

Redis는 모든 데이터를 메모리에 두고, 각 기능에 최적화된 자료구조를 조합하여 접근 경로를 최소화한다. 디스크 I/O를 피하는 것만으로 빠른 게 아니라, 메모리 안에서도 원하는 데이터를 찾는 단계 수를 줄이는 것이 핵심이다.

이 프로젝트는 실제 Redis를 복제하거나 같은 속도를 내는 것이 목적이 아니다. Python으로 핵심 동작을 직접 구성하면서, 단순한 전체 순회 대신 여러 자료구조를 조합하는 이유를 코드 수준에서 이해하는 것이 목표다.

## 해시맵 — 평균 O(1) 키 조회

### 해시 함수와 버킷

키 문자열의 UTF-8 바이트를 직접 순회하며 다항 누적 방식(`hash = hash * 31 + byte`)으로 해시값을 계산한다. 결과를 버킷 수로 나눈 나머지가 버킷 인덱스가 된다.

해시 함수는 충돌을 제거하는 것이 아니라 키를 가능한 한 고르게 분산시켜 체인의 평균 길이를 줄이는 역할을 한다. 단순 바이트 합산과 달리 문자 순서를 반영하여 `"ab"`와 `"ba"` 같은 키가 같은 버킷에 몰리는 충돌을 줄인다.

### 충돌 해결 — 체이닝

같은 버킷 인덱스를 얻은 서로 다른 키들은 해당 버킷의 이중 연결 리스트에 함께 저장된다. 조회 시 해시로 버킷을 선택한 뒤 그 버킷의 체인만 순회하므로, 전체 키를 순회하는 것보다 탐색 범위가 좁다.

### 로드 팩터와 리사이징

로드 팩터(`저장된 키 수 / 버킷 수`)가 0.75를 초과하기 전에 버킷 수를 2배로 확장한다. 확장 후 모든 기존 키를 새 버킷 수로 다시 해싱하여 재배치한다. 이렇게 평균 체인 길이를 제어하여 조회가 O(1)에 가깝게 유지된다.

## 이중 연결 리스트 — O(1) LRU 추적

### 구조

더미 head/tail 사이에 실제 데이터 노드를 저장한다. 각 노드는 `prev`, `next`, `data` 필드를 가지며, 어떤 노드든 앞뒤 포인터만 변경하면 O(1)에 삽입·삭제·이동이 가능하다.

### 해시맵과의 조합으로 O(1) LRU가 가능한 이유

해시맵은 `key → LRU 노드 참조`를 저장한다. GET이나 SET이 성공하면:

1. 해시맵에서 키에 대응하는 노드를 O(1)에 찾는다.
2. 그 노드를 이중 연결 리스트에서 O(1)에 분리한다.
3. 리스트 맨 앞에 O(1)에 다시 연결한다.

리스트 자체는 키를 순회하여 노드를 찾지 않는다. 해시맵이 노드 참조를 직접 제공하므로 탐색 없이 포인터 변경만으로 순서를 갱신한다. 리스트를 단독으로 사용하면 키를 찾는 데 O(N)이 걸리지만, 해시맵과 조합하면 전체 흐름이 O(1)이 된다.

### 메모리 제한과 LRU 퇴출

`maxmemory > 0`이고 `SET` 이후 `used_memory`가 제한을 초과하면, 리스트의 tail 쪽(가장 오래 사용되지 않은 키)부터 `used_memory ≤ maxmemory`가 될 때까지 제거한다. `used_memory`는 `Σ(len(utf8(key)) + len(utf8(value)))`로 계산하며, 자료구조 오버헤드는 포함하지 않는다.

## 최소 힙 — TTL 만료 관리에 적합한 이유

### 왜 힙인가

TTL 만료 관리에서 필요한 연산은 "가장 빨리 만료되는 키를 빠르게 찾기"와 "새 만료 예약을 빠르게 추가하기"다. 최소 힙은 루트에서 최솟값을 O(1)에 확인하고, 삽입과 삭제를 O(log N)에 처리한다.

전체 만료 목록을 매번 순회하면 O(N)이지만, 힙을 사용하면 만료된 항목만 루트에서 꺼내면 되므로 정리 비용이 만료된 수에 비례한다.

### 배열 기반 완전 이진 트리

별도의 트리 노드와 포인터 없이 배열 인덱스 관계(`부모: (i-1)//2`, `왼쪽: 2i+1`, `오른쪽: 2i+2`)로 완전 이진 트리를 표현한다. 각 부모의 만료 시각이 자식 이하가 되도록 불변식을 유지한다.

### Lazy Deletion 전략

`EXPIRE`를 다시 호출하면 TTL 해시맵의 값을 새 `expire_at`으로 갱신하고, 새 힙 항목을 추가하되 기존 항목은 제거하지 않는다. 힙 루트를 처리할 때 현재 TTL과 일치하지 않으면 오래된 항목으로 판단하여 힙에서만 버린다.

이 방식으로 힙 중간 요소의 임의 검색·삭제 기능 없이도 TTL 갱신과 취소를 O(log N)에 처리한다.

## LRU 퇴출 전체 흐름

```
SET key value 실행
  → used_memory에 새 엔트리 크기 반영
  → maxmemory > 0이고 used_memory 초과?
    → LRU 리스트 tail에서 가장 오래된 노드 선택
    → 노드의 CacheEntry에서 키 획득
    → 데이터 해시맵에서 키 제거
    → LRU 리스트에서 노드 제거
    → TTL 해시맵에서 키 제거 (힙의 과거 예약은 lazy deletion)
    → used_memory 차감, evicted_keys 증가
    → used_memory ≤ maxmemory가 될 때까지 반복
```

### 항목 2 — 자료구조 구현 설명

**이중 연결 리스트의 O(1) 동작 원리**

각 노드가 prev, next, data를 가지며, 더미 head/tail 사이에만 실제 노드가 존재한다. 삽입·삭제·이동 시 대상 노드의 앞뒤 포인터만 변경하면 되므로 리스트 크기와 무관하게 O(1)이다. 더미 노드 덕분에 빈 리스트나 경계 노드를 특별 분기할 필요가 없다.

**해시 함수의 동작**

키 문자열을 UTF-8 바이트로 변환한 뒤, 각 바이트를 `hash = (hash * 31 + byte) % capacity` 형태로 누적한다. 31을 곱하는 다항 누적 방식이므로 문자 순서가 결과에 반영되어 `"ab"`와 `"ba"` 같은 키가 다른 인덱스를 얻는다. 최종 결과가 곧 버킷 인덱스다.

**충돌 해결 — 체이닝**

같은 버킷 인덱스를 얻은 서로 다른 키들은 해당 버킷의 이중 연결 리스트에 함께 저장된다. 조회 시 해시로 버킷을 선택하고 그 체인만 순회하여 키를 비교한다. 이중 연결 리스트를 재사용하므로 체인 노드의 삭제도 O(1)이다.

**로드 팩터 0.75 초과 시 리사이징 절차**

1. 새 키를 넣기 전에 `(size + 1) / capacity > 0.75`인지 확인한다.
2. 초과할 예정이면 버킷 수를 2배로 늘린 빈 배열을 만든다.
3. 기존 버킷의 모든 엔트리를 순회하며 새 capacity로 해시를 다시 계산하여 재배치한다.
4. 재배치가 끝난 새 배열로 교체한 뒤 신규 키를 삽입한다.

### 항목 3 — 동작 원리 설명

**해시맵 + 이중 연결 리스트가 둘 다 필요한 이유**

- 해시맵: 키로 O(1)에 대응하는 LRU 노드 참조를 찾는다.
- 이중 연결 리스트: 노드의 포인터만 바꿔 O(1)에 순서를 변경하고, tail 쪽에서 가장 오래된 항목을 O(1)에 꺼낸다.

리스트만 있으면 키를 찾는 데 O(N)이 걸리고, 해시맵만 있으면 "가장 오래된 키"를 알 수 없다. 둘을 조합해야 조회와 순서 갱신 모두 O(1)이 된다.

**O(1) LRU 달성 원리**

1. GET/SET → 해시맵에서 키의 LRU 노드를 O(1)에 찾는다.
2. 해당 노드를 리스트에서 분리(포인터 변경)하고 맨 앞에 재연결한다.
3. 퇴출 시 tail.prev가 가장 오래된 노드이므로 O(1)에 접근하여 제거한다.

**힙을 TTL에 사용한 이유**

"가장 빨리 만료되는 키"를 빠르게 찾아야 한다. 최소 힙은 루트에서 최솟값을 O(1)에 확인하고, 삽입/삭제를 O(log N)에 처리한다. 만료 목록을 매번 전체 순회하면 O(N)이지만, 힙을 사용하면 루트만 확인하고 만료된 것만 꺼내면 된다.

**메모리 초과 시 eviction 흐름**

```
SET key value 실행
→ used_memory += len(utf8(key)) + len(utf8(value))
→ maxmemory > 0이고 used_memory > maxmemory?
  → LRU 리스트 tail.prev에서 가장 오래된 노드 선택
  → 노드의 CacheEntry에서 키 획득
  → data_map에서 키 제거, lru_list에서 노드 제거, expiry_map에서 키 제거
  → used_memory -= 제거한 키+값 바이트
  → evicted_keys += 1
  → used_memory ≤ maxmemory 될 때까지 반복
```

**GET 명령어 전체 흐름**

1. `_purge_expired()` — 힙에서 만료된 키를 먼저 정리한다.
2. `data_map.get(key)` — 해시맵에서 LRU 노드를 찾는다.
3. 키가 없으면 → None 반환, LRU 변경 없음.
4. 키가 있으면 → 노드를 LRU 리스트 맨 앞으로 이동(최근 사용 표시) → 값 반환.
5. 만료로 삭제된 경우는 2번에서 이미 없으므로 LRU 갱신이 발생하지 않는다.

### 항목 4 — 설계 확장 질문

**LRU 대신 LFU(Least Frequently Used) 정책을 구현한다면?**

LFU는 "가장 적게 사용된 키"를 퇴출하므로, 각 키에 접근 횟수(frequency)를 추가로 관리해야 한다. 변경 사항:

- CacheEntry에 `freq` 필드를 추가한다.
- 단일 LRU 리스트 대신, frequency별로 이중 연결 리스트를 두는 구조가 필요하다. (frequency → 해당 빈도의 키들을 담은 리스트)
- 현재 최소 frequency를 추적하는 변수를 별도로 유지한다.
- 퇴출 시 최소 frequency 리스트의 tail에서 제거한다.
- GET/SET 성공 시 해당 키의 freq를 1 증가시키고, 기존 freq 리스트에서 분리하여 freq+1 리스트로 이동한다.

해시맵은 그대로 사용하되, LRU 리스트 하나가 "frequency별 리스트 맵 + min_freq 변수"로 교체되는 구조다.

**데이터 10만 건에서 병목이 될 수 있는 부분과 개선**

1. **리사이징 비용** — 초기 capacity가 8이므로 10만 건까지 약 14회 리사이징이 발생하고, 매번 전체 재해싱이 필요하다. 개선: 서비스에서 예상되는 데이터 규모에 맞춰 초기 capacity를 크게 잡으면 리사이징 횟수를 줄일 수 있다. (예: `HashMap(initial_capacity=131072)`)

2. **`_purge_expired()` 정리 비용** — TTL 갱신이 잦으면 힙에 오래된 항목이 쌓인다. 한 번의 정리에서 무효 항목을 연속으로 pop하는 비용이 발생할 수 있다. 개선: 한 번의 정리에서 처리할 최대 수를 제한하고 나머지는 다음 호출로 분산하는 방식이 있다.

3. **`KEYS` 명령** — 전체 버킷을 순회하므로 O(N)이다. 10만 건이면 체감될 수 있다. 개선: 실제 Redis처럼 `SCAN` 커서 방식으로 분할 순회를 제공하면 한 번에 모든 키를 반환하지 않아도 된다.

메모리 관점에서는 노드·포인터 등 자료구조 오버헤드가 단순 리스트 저장보다 크지만, 이는 O(1) 조회·삽입 속도를 얻기 위한 트레이드오프이며 메모리 사용량 자체보다 "메모리 대비 얻는 시간 복잡도 개선"이 타당한 비교 기준이다.
