# Mini Redis 구현 계획

이 문서는 `Problem.md`의 요구사항을 구현 항목과 일대일로 대응시키며 작성한다.
각 항목은 질의응답을 통해 설계 의도와 구현 방법을 확인한 뒤 확정한다.

## 작성 원칙

- 아직 합의하지 않은 구현 세부사항은 미리 확정하지 않는다.
- 각 요구사항마다 무엇을 만들고 어떻게 동작시킬지 기록한다.
- 자료구조별 책임과 자료구조 사이의 연결 관계를 구분한다.
- 필수 요구사항을 먼저 계획하고 보너스 과제는 별도로 다룬다.
- 마지막에는 Mini Redis의 목적과 Redis의 속도를 체감하는 방법을 큰 관점에서 정리한다.

## 1. 이중 연결 리스트

### 1.1 LRU 노드의 데이터와 소유 관계

- `DoublyLinkedListNode`는 요구사항에 맞게 `prev`, `next`, `data` 필드를 가진다.
- `data`에는 키와 값을 함께 표현하는 `CacheEntry`를 저장한다.
- 데이터 해시맵은 `key -> DoublyLinkedListNode` 관계를 저장한다.
- 실제 키와 값은 LRU 노드가 소유하고, 해시맵은 같은 노드를 참조한다.
- `GET`은 해시맵에서 노드를 찾은 뒤 노드의 값을 반환하고 동일한 노드를 리스트 앞으로 이동한다.
- 메모리 초과 시 리스트의 마지막 노드에서 키를 얻어 데이터 해시맵에서도 해당 키를 삭제한다.
- 해시맵 체이닝 노드와 LRU 노드는 서로 다른 목적을 가진 별도 노드로 구분한다.

### 1.2 더미 head와 tail

- 데이터가 없는 `head`, `tail` 더미 노드를 항상 유지한다.
- 빈 리스트에서는 `head.next == tail`, `tail.prev == head`가 성립한다.
- `head.prev`와 `tail.next`는 `None`으로 유지한다.
- 실제 데이터 노드는 항상 `head`와 `tail` 사이에만 존재한다.
- `size`에는 더미 노드를 포함하지 않는다.
- 첫 노드와 마지막 노드를 별도 분기하지 않고 동일한 포인터 변경으로 삽입·삭제한다.
- 이 구조를 바탕으로 앞뒤 삽입·삭제와 임의 노드 이동을 모두 O(1)에 처리한다.

### 1.3 키 기반 삭제와 노드 기반 삭제의 역할 분리

- `MiniRedis` 계층의 삭제 명령은 사용자에게서 `key`를 받는다.
- 데이터 해시맵에서 `key`에 대응하는 LRU 노드 참조를 평균 O(1)에 조회한다.
- `DoublyLinkedList.remove_node(node)`에는 조회한 노드 객체를 직접 전달한다.
- 연결 리스트 자체는 키 탐색이나 해시맵 조회를 담당하지 않고 포인터 연결만 변경한다.
- 리스트가 키를 직접 순회하여 노드를 찾으면 O(n)이 되므로 사용하지 않는다.
- 전체 흐름은 `key 조회 -> 노드 연결 해제 -> 해시맵 엔트리 삭제`로 구성한다.

### 1.4 포인터 변경 헬퍼와 size 관리

- 포인터 연결만 담당하는 비공개 헬퍼를 둔다.
- `_link_between(node, prev_node, next_node)`는 두 노드 사이에 `node`를 연결한다.
- `_unlink(node)`는 앞뒤 노드를 직접 연결하고 `node`를 분리한다.
- 두 헬퍼는 `size`를 변경하지 않는다.
- `insert_front`, `insert_back`, `remove_front`, `remove_back`, `remove_node`가 실제 삽입·삭제에 맞게 `size`를 변경한다.
- `move_to_front`는 `_unlink`와 `_link_between`을 조합하되 `size`는 변경하지 않는다.
- LRU 리스트에서는 신규 `SET`, 삭제·만료·퇴출, 성공한 `GET`에 따라 삽입·삭제·이동이 발생한다.

### 1.5 삽입 메서드의 입력과 반환

- `insert_front(data)`와 `insert_back(data)`가 내부에서 새 노드를 생성한다.
- 두 메서드는 생성하고 연결한 `DoublyLinkedListNode`를 반환한다.
- `MiniRedis`는 키와 값을 가진 `CacheEntry`를 `data`로 전달하고, 반환된 노드 참조를 데이터 해시맵에 저장한다.
- 연결 리스트는 `key`, `value`의 구체적인 구조를 알지 않고 임의의 `data`를 저장하는 독립 자료구조로 유지한다.
- LRU에서는 새 키를 저장할 때 주로 `insert_front`를 사용하지만, 과제 요구사항에 따라 `insert_back`도 일반 메서드로 구현한다.

### 1.6 삭제 메서드의 반환

- `remove_front()`와 `remove_back()`은 연결을 해제한 노드 객체를 반환한다.
- `remove_node(node)`도 전달받아 제거한 노드 객체를 반환한다.
- 노드 중심 반환 방식은 삽입 메서드가 생성한 노드를 반환하고 이동 메서드가 노드 참조를 받는 설계와 일관된다.
- LRU 퇴출 시 `remove_back()`이 반환한 노드의 `data.key`를 사용해 데이터 해시맵과 다른 메타데이터에서도 같은 키를 제거한다.
- 빈 리스트에서 `remove_front()` 또는 `remove_back()`을 호출하면 `IndexError`를 발생시킨다.
- 빈 리스트 삭제를 정상 흐름으로 숨기지 않고 호출자의 논리 오류나 내부 불변식 위반을 즉시 드러낸다.
- 노드 객체를 반환하므로 `data=None`인 정상 노드와 빈 리스트를 구분하는 데 반환값 `None`이 꼭 필요한 것은 아니다.

## 2. 체이닝 해시맵

### 2.1 버킷과 충돌 체이닝

- 고정 길이 버킷 테이블은 제한적으로 허용된 Python `list`로 구성한다.
- 각 버킷은 `None` 또는 기존에 구현한 `DoublyLinkedList`를 참조한다.
- 빈 버킷은 `None`으로 두고 최초 삽입 시 연결 리스트를 생성하여 불필요한 더미 노드를 줄인다.
- 버킷 리스트의 각 노드에는 `HashEntry(key, value)`를 `data`로 저장한다.
- 같은 버킷 인덱스를 얻은 키들은 해당 연결 리스트에 함께 저장하여 충돌을 해결한다.
- 탐색은 해시로 버킷을 선택한 뒤 그 버킷의 `HashEntry.key`만 순회한다.
- 삭제는 버킷에서 대상 노드를 찾은 뒤 `DoublyLinkedList.remove_node(node)`를 재사용한다.
- 데이터 해시맵의 `HashEntry.value`에는 실제 값이 아니라 대응하는 LRU 노드 참조가 들어간다.
- 체이닝 노드와 LRU 노드는 동일한 연결 리스트 클래스로 만들어지지만 서로 다른 노드 객체이며, 하나의 노드를 두 리스트에 동시에 연결하지 않는다.

### 2.2 직접 구현하는 해시 함수

- Python 내장 `hash()`를 사용하지 않고 문자열 키의 UTF-8 바이트를 직접 순회한다.
- `hash_value = (hash_value * 31 + byte) % capacity` 형태의 다항 누적 방식을 사용한다.
- 단순 바이트 합산과 달리 문자 순서를 반영하여 `"ab"`와 `"ba"` 같은 키가 같은 결과를 얻는 단순 충돌을 줄인다.
- 최종 결과는 항상 현재 `capacity` 범위의 버킷 인덱스가 된다.
- 해시 함수는 충돌을 제거하는 것이 아니라 키를 가능한 한 고르게 분산시켜 체인의 평균 길이를 줄이는 역할을 한다.
- 버킷 수가 변경되면 같은 키의 인덱스도 달라질 수 있으므로 리사이징 시 모든 키를 다시 해싱한다.

### 2.3 put의 신규 삽입과 기존 키 갱신

- `put(key, value)`는 해시로 선택한 버킷의 체인을 먼저 탐색한다.
- 같은 키가 이미 있으면 새 `HashEntry`를 만들지 않고 기존 엔트리의 `value`만 변경한다.
- 기존 키 갱신에서는 `size`와 로드 팩터가 변하지 않는다.
- 서로 다른 키가 같은 버킷에 배정된 경우에만 새 엔트리를 체인에 추가한다.
- 새 키를 추가한 경우에만 `size`를 1 증가시키고 로드 팩터에 반영한다.
- 동일한 키를 중복 저장하지 않아 `get`, `remove`, `contains`의 결과를 명확하게 유지한다.

### 2.4 로드 팩터와 버킷 확장

- 로드 팩터는 `size / capacity`로 계산한다.
- 로드 팩터가 정확히 0.75인 상태는 허용한다.
- 새 키를 넣기 전에 `(size + 1) / capacity > 0.75`인지 확인한다.
- 제한을 초과할 예정이면 실제 삽입 전에 버킷 수를 2배로 확장한다.
- 기존 키 갱신은 `size`가 늘지 않으므로 불필요한 확장을 수행하지 않는다.
- 새 용량으로 빈 버킷 테이블을 만든 뒤 모든 기존 `HashEntry`를 순회한다.
- 버킷 인덱스는 현재 `capacity`를 사용한 나머지 연산으로 결정되므로, 용량 변경 후 각 키를 다시 해싱하여 새 버킷에 삽입한다.
- 재배치 과정에서는 확장 검사를 다시 실행하지 않는 내부 삽입 로직을 사용하고 전체 `size`는 기존 값으로 유지한다.
- 재배치가 끝난 새 버킷 테이블로 기존 테이블을 교체한 다음 신규 키를 삽입한다.

### 2.5 공통 탐색과 None 값의 구분

- `_find_node(key)` 비공개 헬퍼로 해당 키를 가진 버킷의 연결 리스트 노드를 찾는다.
- 키가 존재하면 `HashEntry.value`가 `None`이어도 실제 노드 객체를 반환한다.
- 키가 없을 때만 `_find_node(key)`가 `None`을 반환한다.
- `contains(key)`는 값이 아니라 `_find_node(key) is not None`으로 존재 여부를 판단한다.
- `get(key)`는 노드를 찾으면 `HashEntry.value`를 반환하고, 키가 없으면 `None`을 반환한다.
- 따라서 `get()` 결과만으로 저장된 `None`과 없는 키를 구분하지 않으며, 구분이 필요하면 `contains()`를 함께 사용한다.
- `put`, `get`, `remove`, `contains`가 같은 탐색 헬퍼를 재사용하여 체인 순회 로직의 중복을 줄인다.

### 2.6 remove의 결과와 상태 변경

- `remove(key)`는 삭제 성공 여부를 `bool`로 반환한다.
- 키가 없으면 아무 상태도 변경하지 않고 `False`를 반환한다.
- 키가 있으면 해당 버킷 노드를 연결 리스트에서 제거하고 `size`를 1 감소시킨 뒤 `True`를 반환한다.
- 삭제 결과가 저장된 값과 독립적이므로 값으로 `None`을 허용해도 성공 여부가 모호하지 않다.
- 삭제 후 버킷 연결 리스트가 비면 해당 버킷을 다시 `None`으로 바꾼다.
- `MiniRedis`는 이 결과를 이용해 `DEL`의 `(integer) 1` 또는 `(integer) 0`을 결정한다.

### 2.7 keys와 size

- `keys()`는 버킷 배열을 처음부터 끝까지 순회한다.
- 비어 있지 않은 각 버킷에서는 더미 노드를 제외한 모든 체이닝 노드를 순회하여 `HashEntry.key`를 결과에 추가한다.
- 키의 정렬이나 특정 출력 순서는 보장하지 않는다.
- 결과 수집에는 일반 Python `list`를 사용한다. 이는 내장 Key-Value 컬렉션으로 해시맵을 대체하는 것이 아니라 명령 결과를 담는 용도이므로 제약에 어긋나지 않는다.
- 시간 복잡도는 버킷 수를 `capacity`, 저장된 키 수를 N이라 할 때 O(capacity + N)이다.
- 로드 팩터를 제한하여 capacity가 N에 비례하므로 일반적으로 O(N)으로 설명할 수 있다.
- 현재 엔트리 수는 `_size` 필드로 별도 관리하고 `size()`는 이를 그대로 반환하여 O(1)에 동작한다.
- 신규 키 삽입에서만 `_size`를 증가시키고, 실제 삭제 성공에서만 감소시키며, 기존 키 갱신과 리사이징 중 재배치에서는 변경하지 않는다.

## 3. 최소 힙

### 3.1 배열 기반 완전 이진 트리

- 최소 힙의 내부 저장소로 0-based Python `list`를 사용한다.
- Python `list`는 힙 알고리즘을 대신하는 Key-Value 컬렉션이 아니며 동적 배열 직접 구현은 보너스이므로 필수 구현에서 사용할 수 있다.
- 인덱스 `i`의 부모는 `(i - 1) // 2`로 계산한다.
- 왼쪽 자식은 `2 * i + 1`, 오른쪽 자식은 `2 * i + 2`로 계산한다.
- 별도의 트리 노드와 포인터 없이 배열 인덱스 관계로 완전 이진 트리를 표현한다.
- 각 부모의 만료 시각이 자식의 만료 시각 이하가 되도록 최소 힙 불변식을 유지한다.

### 3.2 push와 _heapify_up

- 힙 요소는 `(expire_at, key)`를 표현하며 우선순위는 `expire_at`으로 비교한다.
- `push(item)`은 새 요소를 배열 마지막에 추가한다.
- `_heapify_up(index)`는 현재 요소의 만료 시각이 부모보다 작으면 두 요소를 교환한다.
- 교환 후 부모 인덱스로 이동하여 루트에 도달하거나 부모의 만료 시각이 현재 요소 이하가 될 때까지 반복한다.
- 만료 시각이 같은 요소끼리는 추가 교환하지 않아도 되며 키 사이의 순서는 보장하지 않는다.
- 완전 이진 트리의 높이가 O(log N)이므로 `push`의 최악 시간 복잡도는 O(log N)이다.

### 3.3 pop과 _heapify_down

- `pop()`은 최소값인 루트 요소를 반환 대상으로 보관한다.
- 배열의 마지막 요소를 루트로 옮긴 뒤 마지막 칸을 제거하여 완전 이진 트리 형태를 유지한다.
- 요소가 남아 있으면 루트부터 `_heapify_down(0)`을 실행한다.
- `_heapify_down`은 존재하는 왼쪽·오른쪽 자식 중 만료 시각이 더 작은 자식을 선택한다.
- 현재 요소의 만료 시각이 선택한 자식보다 크면 교환하고 해당 자식 인덱스에서 비교를 반복한다.
- 자식이 없거나 현재 요소가 더 작은 자식 이하이면 중단한다.
- 트리의 높이만큼 이동하므로 `pop`의 최악 시간 복잡도는 O(log N)이다.

### 3.4 peek, size와 빈 힙 처리

- `peek()`은 배열의 첫 요소를 반환하므로 O(1)에 동작한다.
- `size()`는 O(1)인 `len(self._items)`를 반환한다.
- 힙의 내부 배열 길이는 저장된 요소 수와 같으므로 별도의 `_size` 필드를 두지 않는다.
- 해시맵은 버킷 배열 길이와 엔트리 수가 다르므로 `_size`가 필요하지만, 힙에는 이 차이가 없다.
- 빈 힙에서 `peek()` 또는 `pop()`을 호출하면 `IndexError`를 발생시킨다.
- TTL 정리 로직은 `peek()`이나 `pop()` 전에 `size() > 0`을 확인하여 정상 흐름에서 빈 힙 예외가 발생하지 않도록 한다.

### 3.5 TTL 힙 요소의 만료 시각

- `EXPIRE key seconds`의 상대 시간은 설정 시점에 `expire_at = 현재 시각 + seconds`인 절대 마감 시각으로 변환한다.
- 최소 힙에는 `(expire_at, key)` 요소를 저장한다.
- 서로 다른 시점에 설정된 TTL도 `expire_at`끼리 직접 비교하여 실제 만료 순서를 결정한다.
- 힙의 루트에는 현재 등록된 요소 중 `expire_at`이 가장 이른 항목이 위치한다.
- 남은 TTL은 `expire_at - 현재 시각`을 바탕으로 계산한다.

### 3.6 TTL 측정 시계

- 실행 중 경과 시간 측정에는 `time.monotonic()`을 사용한다.
- `time.monotonic()`은 시스템 날짜·시간이 변경되어도 뒤로 가지 않으므로 실행 중 TTL이 시계 보정에 영향을 받지 않는다.
- 값 자체를 실제 날짜로 해석하지 않고 `expire_at = time.monotonic() + seconds`와 두 시각의 차이만 사용한다.
- 이번 과제는 데이터 영속성과 재시작 복구를 구현하지 않으므로 프로세스를 넘어 `expire_at`을 보존할 필요가 없다.
- 실제 Redis는 영속화와 재시작을 고려해 절대 Unix 만료 시각을 사용하며, `monotonic()` 선택은 과제 범위에 맞춘 단순화임을 문서화한다.

### 3.7 TTL 갱신과 lazy deletion

- 현재 유효한 만료 시각은 별도의 커스텀 해시맵에 `key -> expire_at`으로 저장한다.
- `EXPIRE`를 다시 호출하면 TTL 해시맵의 값을 새 `expire_at`으로 갱신하고 새 `(expire_at, key)`를 최소 힙에 추가한다.
- 기존 힙 항목은 중간에서 검색하거나 제거하지 않고 그대로 둔다.
- 힙 루트를 처리할 때 TTL 해시맵에 키가 없으면 TTL이 취소된 오래된 항목이므로 힙에서만 제거한다.
- TTL 해시맵의 현재 `expire_at`과 힙 항목의 `expire_at`이 다르면 갱신 전의 오래된 항목이므로 힙에서만 제거한다.
- 현재 TTL과 일치하는 유효 항목이면서 `expire_at <= now`이면 힙에서 제거한 뒤 실제 키와 현재 TTL을 삭제한다.
- 현재 TTL과 일치하는 유효 항목이면서 아직 만료되지 않았다면 가장 빠른 유효 만료도 미래이므로 정리를 중단한다.
- 유효성 검사 후 현재 시각을 비교해야 하며, 오래된 힙 항목을 제거할 때는 실제 키를 삭제하지 않는다.
- 이 lazy deletion 전략으로 힙 중간 요소의 임의 검색·삭제 기능 없이 TTL 갱신과 취소를 처리한다.

### 3.8 TTL 남은 초 계산

- `TTL`은 먼저 현재 시각이 `expire_at` 이상인지 확인한다.
- 이미 만료됐다면 실제 키를 삭제하고 존재하지 않는 키의 결과인 `(integer) -2`를 반환한다.
- 아직 유효하다면 `math.ceil(expire_at - now)`로 남은 초를 올림하여 반환한다.
- 올림을 사용해 `EXPIRE key 3` 직후에는 직관적으로 3을 반환하고, 만료 직전까지 최소 1을 반환한다.
- `TTL 0`을 반환하는 중간 상태를 두지 않고, 만료 시점부터는 키를 삭제한 뒤 -2로 처리한다.

## 4. MiniRedis 핵심 상태와 공통 동작

### 4.1 자료구조와 상태의 소유 관계

- `data_map`은 커스텀 `HashMap` 인스턴스이며 `key -> LRU 노드 참조`를 저장한다.
- `lru_list`는 하나의 `DoublyLinkedList` 인스턴스이며 각 노드의 `CacheEntry`가 실제 키와 값을 소유한다.
- 데이터 저장 리스트와 LRU 리스트를 따로 만들지 않고 같은 노드로 실제 데이터와 최근 사용 순서를 함께 관리한다.
- `expiry_map`은 별도의 커스텀 `HashMap` 인스턴스이며 `key -> 현재 유효한 expire_at`을 저장한다.
- `expiry_heap`은 `MinHeap` 인스턴스이며 현재 및 오래된 `(expire_at, key)` 예약을 모두 담고 lazy deletion으로 정리한다.
- `used_memory`는 현재 저장된 모든 키와 값의 공식상 바이트 합으로 0에서 시작한다.
- `maxmemory`는 메모리 제한이며 기본값 0을 무제한으로 해석한다.
- `evicted_keys`는 LRU 정책으로 퇴출된 키의 누적 수이며 0에서 시작한다.
- 버킷 배열, capacity, 로드 팩터, 해시맵 `_size`는 각 `HashMap` 내부 상태로 캡슐화하고 `MiniRedis`가 직접 관리하지 않는다.

### 4.2 공통 키 삭제 헬퍼

- `DEL`, TTL 만료, 즉시 만료, LRU 퇴출에서 같은 `_delete_key(key, count_as_eviction=False)` 헬퍼를 사용한다.
- 데이터 해시맵에서 LRU 노드를 조회하고, 키가 없으면 상태를 바꾸지 않은 채 `False`를 반환한다.
- 노드의 `CacheEntry`로 키와 값의 UTF-8 바이트 크기를 계산하여 `used_memory`에서 차감한다.
- 데이터 해시맵에서 키를 제거하고 LRU 리스트에서 해당 노드를 제거한다.
- TTL 해시맵에서도 키를 제거하되 최소 힙 중간의 예약은 그대로 두어 lazy deletion으로 처리한다.
- 메모리 제한 초과로 LRU 키를 퇴출할 때만 `count_as_eviction=True`로 호출하여 `evicted_keys`를 증가시킨다.
- 사용자 `DEL`, TTL 만료, `EXPIRE`의 즉시 만료는 `evicted_keys`에 포함하지 않는다.
- 삭제 성공 시 `True`, 없는 키이면 `False`를 반환하여 `DEL` 결과에도 재사용한다.

### 4.3 공통 만료 정리

- 모든 공개 명령의 본래 동작 전에 `_purge_expired()`를 호출한다.
- 한 번의 정리 과정에서는 `now = time.monotonic()`을 한 번 구해 동일한 기준 시각으로 비교한다.
- TTL 해시맵에 키가 없거나 현재 만료 시각과 일치하지 않는 힙 루트는 오래된 항목이므로 힙에서만 제거한다.
- 현재 TTL과 일치하고 `expire_at <= now`인 루트는 힙에서 제거한 뒤 공통 삭제 헬퍼로 실제 키를 삭제한다.
- 가장 빠른 유효 루트가 아직 만료되지 않았다면 이후 항목도 만료 전이므로 반복을 중단한다.
- 이 정리로 접근되지 않은 만료 키도 `DBSIZE`, `KEYS`, `INFO memory`에서 제외한다.
- TTL 만료 삭제는 LRU 퇴출이 아니므로 `evicted_keys`를 증가시키지 않는다.

## 5. String 명령어

### 5.1 SET key value

- 명령 실행 전 해당 키의 만료 여부를 확인하여 만료된 기존 키는 먼저 정리한다.
- 공식 메모리 크기는 `len(key.encode("utf-8")) + len(value.encode("utf-8"))`로 계산한다.
- `maxmemory > 0`이고 새 단일 엔트리 크기 자체가 `maxmemory`를 초과하면 상태를 변경하지 않고 OOM 오류를 반환한다.
- 기존 키 덮어쓰기에서도 새 크기 검사를 먼저 수행하여 OOM이면 기존 값과 기존 TTL을 그대로 보존한다.
- 새 키이면 `CacheEntry`를 LRU 리스트 앞에 삽입하고 반환된 노드를 데이터 해시맵에 저장한다.
- 기존 키이면 LRU 노드의 값을 변경하고 해당 노드를 리스트 앞으로 이동한다.
- 기존 키를 정상적으로 덮어쓴 경우에만 TTL 해시맵에서 기존 TTL을 제거하여 TTL을 초기화하며, 힙의 과거 예약은 lazy deletion으로 남긴다.
- `used_memory`는 새 키에서 새 엔트리 크기만큼 증가시키고, 덮어쓰기에서는 `새 엔트리 크기 - 기존 엔트리 크기`만큼 조정한다.
- 저장과 LRU 갱신 후 `maxmemory > 0`이고 사용량이 제한을 넘으면 LRU 리스트 뒤쪽부터 공통 삭제 헬퍼로 퇴출한다.
- `used_memory <= maxmemory`가 될 때까지 반복하며 각 LRU 퇴출마다 `evicted_keys`를 1 증가시킨다.
- 핵심 메서드는 정상 완료 시 `True`, 단일 엔트리 OOM이면 `OutOfMemoryError`를 발생시킨다.
- CLI는 이를 각각 `OK`, `(error) OOM command not allowed when used_memory > 'maxmemory'`로 출력한다.

### 5.2 GET key

- 공통 만료 정리 후 데이터 해시맵에서 키에 대응하는 LRU 노드를 조회한다.
- 키가 없으면 핵심 메서드는 `None`을 반환하고 LRU를 변경하지 않으며, CLI는 `(nil)`로 출력한다.
- 키가 있으면 핵심 메서드는 노드의 `CacheEntry.value`를 반환하고 노드를 LRU 리스트 앞으로 이동하며, CLI는 값을 큰따옴표 형태로 출력한다.
- 실제 값을 반환한 성공한 조회에서만 LRU 순서를 갱신한다.

### 5.3 DEL key

- 공통 만료 정리 후 `_delete_key(key)`를 호출한다.
- 데이터·LRU·TTL 해시맵과 `used_memory`를 함께 정리하고 힙의 과거 예약은 lazy deletion으로 남긴다.
- 핵심 메서드는 삭제 성공 시 1, 키가 없으면 0을 반환하고 CLI는 `(integer) N`으로 출력한다.
- 사용자 삭제이므로 `evicted_keys`는 증가시키지 않는다.

### 5.4 EXISTS key

- 공통 만료 정리 후 데이터 해시맵의 `contains(key)`로 존재 여부를 확인한다.
- 핵심 메서드는 존재하면 1, 없으면 0을 반환하고 CLI는 `(integer) N`으로 출력한다.
- 문제에서 LRU 갱신 대상으로 명시한 명령은 성공한 `SET`과 `GET`이므로 `EXISTS`는 LRU 순서를 바꾸지 않는다.

### 5.5 DBSIZE

- 공통 만료 정리 후 데이터 해시맵의 O(1) `size()`를 사용한다.
- 핵심 메서드는 현재 유효한 키 수를 정수로 반환하고 CLI는 `(integer) N`으로 출력한다.
- 조회만 수행하며 LRU 순서를 바꾸지 않는다.

### 5.6 KEYS

- 공통 만료 정리 후 데이터 해시맵의 `keys()`로 전체 유효 키를 수집한다.
- 키의 정렬이나 특정 순서는 보장하지 않고 CLI에서 배열 형태로 출력한다.
- 키가 없으면 `(empty array)`로 출력한다.
- 전체 순회는 O(N)이며 LRU 순서를 바꾸지 않는다.

## 6. 메모리 관리 명령어

### 6.1 CONFIG SET maxmemory bytes

- `CONFIG SET maxmemory bytes`의 정확한 하위 명령과 인자 개수를 검증한다.
- `bytes`를 정수로 파싱하고 음수이면 `(error) ERR value is not an integer or out of range`를 반환한다.
- 0은 무제한으로 해석하고 양수는 UTF-8 키·값 바이트 합의 최대치로 사용한다.
- 검증에 성공하면 `maxmemory`를 갱신하고 핵심 메서드는 `True`, CLI는 `OK`를 반환한다.
- 새 제한이 현재 `used_memory`보다 작아도 `CONFIG SET` 실행 중 기존 키를 즉시 퇴출하지 않는다.
- 문제에서 명시한 대로 이후 정상적인 `SET`이 완료된 시점에 제한을 초과하면 LRU 퇴출을 실행한다.

### 6.2 INFO memory

- 공통 만료 정리 후 현재 메모리 상태를 출력한다.
- 최소한 `used_memory:<number>`, `maxmemory:<number>`, `evicted_keys:<number>` 세 줄을 포함한다.
- `used_memory`는 Python 객체의 실제 RAM 사용량이 아니라 키·값 UTF-8 바이트 합으로 유지한 논리적 수치다.
- 조회 명령이므로 LRU 순서를 바꾸지 않는다.

## 7. TTL 명령어

### 7.1 EXPIRE key seconds

- 공통 만료 정리 후 `seconds`가 정수인지 검증한다.
- 키가 없으면 핵심 메서드는 0을 반환한다.
- 키가 있고 `seconds <= 0`이면 공통 삭제 헬퍼로 즉시 삭제한 뒤 핵심 메서드는 1을 반환한다.
- 양수이면 `expire_at = time.monotonic() + seconds`를 계산한다.
- TTL 해시맵의 `key -> expire_at`을 삽입 또는 갱신하고 최소 힙에 새 `(expire_at, key)`를 추가한다.
- 이전 힙 예약은 제거하지 않고 lazy deletion으로 처리한다.
- 정상 설정 시 핵심 메서드는 1을 반환하고 LRU 순서는 바꾸지 않으며, CLI는 정수 결과를 `(integer) N`으로 출력한다.
- 즉시 만료와 자연 만료는 LRU 퇴출이 아니므로 `evicted_keys`를 증가시키지 않는다.

### 7.2 TTL key

- 공통 만료 정리 후 데이터 해시맵에 키가 없으면 핵심 메서드는 -2를 반환한다.
- 키는 있지만 TTL 해시맵에 현재 만료 시각이 없으면 핵심 메서드는 -1을 반환한다.
- TTL이 있으면 현재 시각을 다시 확인하고 `now >= expire_at`이면 키를 삭제한 뒤 핵심 메서드는 -2를 반환한다.
- 아직 유효하면 핵심 메서드는 `math.ceil(expire_at - now)`를 반환하고 CLI는 결과를 `(integer) N`으로 출력한다.
- TTL 조회는 데이터 접근으로 간주하지 않아 LRU 순서를 바꾸지 않는다.

## 8. CLI와 오류 처리

### 8.1 입력 파싱과 REPL

- `mini-redis> ` 프롬프트로 `input()`을 반복 호출한다.
- 빈 입력은 실행하지 않고 다음 프롬프트로 넘어간다.
- 입력 문자열은 표준 라이브러리 `shlex.split()`으로 토큰화한다.
- 공백 없는 값과 `"Alice Smith"`처럼 큰따옴표로 감싼 공백 포함 값을 모두 하나의 인자로 지원한다.
- 닫히지 않은 따옴표 등 `shlex.split()` 파싱 실패는 `(error) ERR syntax error`로 출력한다.
- 명령어와 `CONFIG SET`, `INFO memory`의 예약어는 대소문자를 구분하지 않도록 비교 시 대문자로 정규화한다.
- `exit` 또는 `quit`이 단독으로 입력되면 반복을 종료한다.
- EOF 입력도 정상 종료로 처리한다.

### 8.2 명령어 디스패치와 표준 오류

- 파싱한 첫 토큰으로 지원 명령 핸들러를 선택한다.
- 지원하지 않는 명령은 `(error) ERR unknown command '<cmd>'`를 반환한다.
- 각 명령 핸들러는 실행 전에 정확한 인자 개수를 검증한다.
- 인자 개수가 다르면 `(error) ERR wrong number of arguments for '<cmd>' command`를 반환한다.
- `maxmemory`와 `seconds`는 공통 정수 파싱 헬퍼로 변환한다.
- 정수 변환 실패 또는 `maxmemory`의 음수 값에는 `(error) ERR value is not an integer or out of range`를 반환한다.
- `EXPIRE`의 0 이하 정수는 파싱 오류가 아니라 즉시 만료 규칙으로 처리한다.
- 핵심 `MiniRedis` 메서드는 구조화된 실행 결과를 반환하고 CLI 계층이 Redis 스타일 문자열로 출력한다.

### 8.3 핵심 반환값과 CLI 출력의 분리

- `MiniRedis` 핵심 메서드는 출력 문자열을 만들지 않고 실제 Python 값이나 상태를 반환한다.
- `SET`과 `CONFIG SET` 성공은 `True`, `GET`은 값 또는 `None`을 반환한다.
- `DEL`, `EXISTS`, `DBSIZE`, `EXPIRE`, `TTL`은 정수를 반환한다.
- `KEYS`는 키 문자열의 `list`, `INFO memory`는 `used_memory`, `maxmemory`, `evicted_keys`의 튜플을 반환한다.
- 단일 엔트리 메모리 초과는 전용 `OutOfMemoryError`로 핵심 계층에서 CLI 계층에 전달한다.
- CLI는 반환형에 따라 `OK`, `(nil)`, `(integer) N`, 따옴표 문자열, 배열과 메모리 정보로 포맷한다.
- 문자열과 키의 큰따옴표·역슬래시 표시는 표준 라이브러리 `json.dumps(value, ensure_ascii=False)`로 안전하게 이스케이프한다.
- 핵심 테스트는 상태와 Python 반환값을 검증하고 CLI 테스트는 Redis 스타일 출력 문자열을 별도로 검증한다.

## 10. 테스트 계획

### 10.1 테스트 도구와 시간 제어

- Python 표준 라이브러리 `unittest`를 사용하여 외부 테스트 의존성을 추가하지 않는다.
- `MiniRedis` 생성자는 기본 시계로 `time.monotonic`을 사용한다.
- 테스트에서는 호출 가능한 가짜 시계를 주입하고 `advance(seconds)`로 현재 시각을 즉시 이동한다.
- TTL 테스트에서 실제 `sleep()`을 사용하지 않아 테스트를 빠르고 결정적으로 유지한다.

### 10.2 자료구조 단위 테스트

- 테스트 수를 과도하게 늘리지 않고 각 자료구조의 핵심 정상 동작과 대표 경계 조건만 빠르게 검증한다.
- 이중 연결 리스트는 삽입·삭제·이동 후 연결 순서와 `size`를 확인한다.
- 해시맵은 삽입·조회·갱신·삭제와 리사이징 후 조회를 확인한다.
- 최소 힙은 여러 요소를 넣고 `pop()` 결과가 만료 시각 오름차순인지 확인한다.

### 10.3 Mini Redis 통합 테스트

- 기본 명령의 대표 성공·실패 결과를 하나의 짧은 흐름으로 확인한다.
- 작은 메모리 제한에서 접근 순서에 맞는 LRU 키가 퇴출되고 `used_memory`, `evicted_keys`가 갱신되는지 확인한다.
- 가짜 시계로 TTL 설정·만료와 갱신된 과거 힙 항목의 lazy deletion을 확인한다.
- 단일 엔트리 OOM과 UTF-8 바이트 계산을 대표 값으로 확인한다.
- CLI는 정상 명령 하나와 인자 오류·정수 오류·알 수 없는 명령의 표준 출력만 확인한다.
- 성능 시간은 환경에 따라 달라지므로 단위 테스트에서 시간 기준으로 성공·실패를 판정하지 않는다.

### 10.4 간단한 조회 비교

- `lookup_benchmark.py`에 충분히 많은 `(key, value)` 쌍을 일반 Python 리스트와 커스텀 해시맵에 동일하게 준비한다.
- 일반 리스트는 `for`문으로 뒤쪽 키를 찾고, 해시맵은 `get(key)`로 같은 키를 조회한다.
- 같은 조회를 여러 번 반복하고 `time.perf_counter()`로 각 경과 시간을 출력한다.
- 데이터 수와 반복 횟수는 실행이 수 초 안에 끝나면서 차이를 관찰할 수 있는 수준으로 둔다.
- 이 비교는 선형 탐색 O(N)과 해시맵 평균 O(1)의 차이를 관찰하기 위한 학습용이며 실제 Redis 성능 수치로 해석하지 않는다.

## 11. 구현 순서

1. 이중 연결 리스트와 단위 테스트를 구현하여 포인터 불변식과 O(1) 연산 기반을 확정한다.
2. 연결 리스트를 버킷 체인으로 재사용하는 해시맵과 리사이징 테스트를 구현한다.
3. 배열 기반 최소 힙과 위·아래 heapify 테스트를 구현한다.
4. `MiniRedis`의 핵심 상태, 공통 삭제 헬퍼, 만료 정리와 가짜 시계 주입을 구현한다.
5. String 명령, 메모리 제한·LRU 퇴출, TTL 명령 순으로 핵심 기능을 연결한다.
6. `shlex` 기반 CLI 디스패치와 Redis 스타일 출력·오류 처리를 구현한다.
7. 짧은 통합 테스트로 자료구조 사이의 핵심 상태 일관성을 검증한다.
8. 리스트 선형 탐색과 커스텀 해시맵 조회를 비교하는 단일 학습용 스크립트를 작성한다.
9. 중복 로직을 공통 헬퍼로 정리하고 주석·docstring·실행 방법을 최종 검토한다.

## 12. 제약 준수와 제외 범위

- Python 3.8 이상에서 실행되도록 지원하지 않는 최신 문법에 의존하지 않는다.
- `dict`, `set`, `collections`로 데이터 저장, LRU, TTL 또는 체이닝을 대체하지 않는다.
- Python `list`는 버킷 테이블, 힙 배열과 명령 결과처럼 문제에서 허용하거나 필요한 순차 저장 용도로만 사용한다.
- 각 핵심 클래스와 복잡한 포인터·heapify·재해싱 로직에 역할과 불변식을 설명하는 docstring 또는 주석을 작성한다.
- 네트워크 통신, 파일 영속성, 복잡 자료형, 멀티스레딩과 락은 구현하지 않는다.
- 동적 배열, 스택·큐·덱 문서, 이진 트리, BST와 Pub/Sub는 선택 보너스이므로 현재 필수 구현 범위에서 제외한다.

## 13. 이 과제가 하는 일과 Redis의 속도를 이해하는 방법

### 13.1 큰 관점의 목표

Redis는 명령 처리에 필요한 주 데이터를 메모리에 두고, 키 탐색과 각 기능의 목적에 맞는 자료구조를 사용한다. 메모리에 있다는 사실은 디스크 접근을 피하게 하고, 해시맵·연결 리스트·힙은 메모리 안에서 원하는 데이터를 찾고 관리하는 경로를 짧게 만든다. 실제 Redis는 설정에 따라 데이터를 디스크에 영속화할 수 있지만, 이번 Mini Redis는 문제 범위상 실행 중인 Python 프로세스 메모리에만 상태를 유지한다.

이번 과제는 실제 Redis 전체를 복제하거나 같은 속도를 내는 것이 목적이 아니다. Python으로 핵심 동작을 직접 구성하여, Redis 스타일 저장소가 왜 단순한 전체 순회 대신 여러 자료구조를 조합하는지 코드 수준에서 이해하는 것이 목표다.

### 13.2 구현을 통해 확인하는 속도의 근거

- 커스텀 해시맵은 키를 해싱하여 평균 O(1)에 데이터가 있는 버킷으로 접근한다.
- 충돌 시 체이닝으로 같은 버킷의 항목을 구분하고, 로드 팩터가 0.75를 넘기 전에 버킷을 확장해 평균 체인 길이를 제어한다.
- 해시맵에서 얻은 LRU 노드 참조와 이중 연결 리스트를 조합하여 성공한 `GET`·`SET`의 최근 사용 순서 변경을 평균 O(1)에 처리한다.
- 최소 힙은 가장 이른 TTL을 루트에서 O(1)에 확인하고 삽입·삭제 후 O(log N)에 순서를 복구한다.
- `used_memory`와 LRU 리스트의 마지막 노드를 이용해 메모리 제한 초과 시 오래된 키부터 제거한다.

LRU와 TTL은 해시의 내부 기법이 아니다. 체이닝과 리사이징은 해시맵의 충돌·성능 관리 기법이고, LRU는 해시맵과 이중 연결 리스트를 조합한 제거 정책이며, TTL은 현재 만료 정보 해시맵과 최소 힙을 조합한 시간 관리 기능이다.

### 13.3 속도 차이를 체감하는 범위

`lookup_benchmark.py`에서 일반 리스트를 `for`문으로 순회하는 O(N) 조회와 커스텀 해시맵의 평균 O(1) 조회를 충분한 요소 수로 비교한다. 이 한 가지 비교로 데이터가 늘어날수록 전체 순회 비용은 증가하지만 해시 조회 경로는 짧게 유지되는 차이를 관찰한다.

이 결과는 실제 Redis와 Mini Redis의 절대 성능 비교가 아니다. 실제 성능에는 구현 언어, 메모리 표현, 네트워크와 운영체제 등 많은 요소가 개입한다. 여기서는 디스크 기반 데이터베이스와 속도를 재거나 Redis를 벤치마크하지 않고, 적절한 자료구조가 탐색 단계를 줄이는 효과만 학습용으로 확인한다.
