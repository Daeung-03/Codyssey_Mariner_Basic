프로세스의 생존 상태와 자원 사용 패턴을 함께 구분하는 것
  - OOM: 메모리가 시간에 따라 계속 증가하다가, 임계치를 넘으면 프로그램의 MemoryGuard가 프로세스를 종료합니다.
  - CPU 과점유: 특정 프로세스의 CPU 사용률이 급격히 높아지고, 임계치를 넘으면 Watchdog가 종료합니다.
  - Deadlock: 프로세스는 살아 있지만, 스레드들이 락을 기다리며 진행하지 못해 CPU와 메모리 변화, 로그 출력이 멈춥니다.


### Deadlock

Deadlock 상태에서 ps로 PID가 존재하는 것만으로는 왜 원인을 확정할 수 없을까요?
  - PID 존재는 단지 프로세스가 종료되지 않았다는 증거. 아래를 구분 할 수 없다.
  - 정상적으로 요청을 기다리는 유휴 프로세스
  - 느리지만 실제 작업을 진행 중인 프로세스
  - 네트워크나 파일 I/O를 기다리는 프로세스
  - 락을 서로 기다리는 Deadlock 상태

  그래서 Deadlock은 증거를 조합해야 합니다.

  1. ps -ef로 PID가 계속 존재함을 확인한다.
  2. top -H 또는 ps -L로 스레드별 CPU 사용량이 거의 0이고 변화가 없음을 확인한다.
  3. 로그의 마지막 지점이 WAITING 또는 BLOCKED이고, 그 뒤로 진행 로그가 없음을 확인한다.
  4. 여러 스레드가 서로 상대 락을 기다린다는 로그를 근거로 순환 대기를 설명한다.

관측되는 현상

  - CPU가 낮고 변하지 않음: 실행 가능한 연산이 아니라 락 대기 상태이기 때문
  - 메모리가 낮고 변하지 않음: 새 작업이나 데이터 처리가 진행되지 않기 때문
  - 로그가 특정 WAITING/BLOCKED 지점에서 멈춤: 다음 단계로 진입할 스레드가 없음
  - PID는 존재: 프로세스가 크래시하거나 종료된 것은 아님
  -> PID 유지 + 자원/로그 정체 + 락 대기 로그

  - 점유 대기: 각 스레드가 락 하나를 보유한 채 다른 락을 기다림
  - 순환 대기: A는 B가 가진 락을, B는 A가 가진 락을 기다리는 고리
  상호 배제와 비선점

MULTI_THREAD_ENABLE=false
멀티스레드를 비활성화하면 동시에 락을 경쟁할 두 스레드가 없으므로, 동시에 락을 보유하고 다른 락을 기다리는 복수의 실행 흐름이 사라진다. 따라서 Deadlock의 필요 조건인 순환 대기가 성립 X


### OOM

메모리 누수는 프로그램이 작업 중 확보한 메모리를, 더 이상 필요 없어진 뒤에도 해제하거나 참조를 끊지 못해 재사용 불가능한 점유량이 계속 쌓이는 결함
정상적이라면, 작업이 끝나거나 캐시 상한에 도달하면 사용량이 안정화되거나 감소해야한다.

단기 조치 후 Before/After에서 확인할 결론

- MEMORY_LIMIT 상향 후 생존 시간은 늘었다
- 하지만 관제에서 메모리 사용량이 여전히 시간에 따라 상승한다면 누수 패턴은 계속된다
- 따라서 이는 서비스 연속성을 잠시 확보하는 우회책이고, 근본 해결은 데이터를 해제하거나 누적 구조를 수정하는 것이다

관측 시점
  같은 종류의 작업 또는 특별한 입력 변화가 없는데 메모리가 시간에 따라 지속 상승한다.

  시간        프로세스 메모리
  시작        45 MB
  1분 후      80 MB
  2분 후      116 MB
  3분 후      151 MB
  ...
  종료 직전   MEMORY_LIMIT 근처
  정상적인 작업량 변화와 무관하게 프로세스의 RSS/메모리 사용량이 지속적으로 누적되고, 종료 후 다시 실행하면 낮은 값에서 시작하는지

### CPU 과점유

특정 프로세스가 CPU 실행 시간을 과도하게 점유해 다른 작업의 실행 기회를 줄이는 상태.
agent-leak-app만 CPU 사용시간이 높고, 

프로세스별 CPU 사용률을 제시해야 정확한 근거가 된다. 아래와 같은 상황이 있을 수 있음(원인이 아닌 경우)

  - agent-leak-app 하나가 대부분을 사용한다.
  - agent-leak-app은 95%지만, 다른 프로세스들도 많이 사용해 전체 부하가 높다.
  - 다른 프로세스가 먼저 시스템을 포화시켰고, 앱의 작업 지연이 부수적으로 관측된다.
  - 멀티코어 환경에서는 CPU 사용률 표기 기준이 도구마다 달라서, 한 코어의 95%인지 전체 코어 기준 95%인지도 확인해야 한다.

원인 분석 -> 시스템 전체 부하의 주범임을 특정해야함.

  ps/top 결과:
  agent-leak-app  95% CPU
  다른 주요 프로세스  1~3% CPU


### 각 CASE 별 구체적으로 수집해야 하는 증거

 1. OOM
      - 시간별 agent-leak-app의 메모리 사용량이 지속 상승한 monitor.sh 로그
      - 종료 직전 Memory limit exceeded, SELF-TERMINATED 등 MemoryGuard 로그
      - MEMORY_LIMIT 변경 전후의 종료 시점 또는 생존 시간 비교

  2. CPU 과점유
      - top 또는 ps에서 agent-leak-app의 CPU 사용률이 다른 주요 프로세스보다 두드러지게 높다는 증거
      - 시간 흐름상 CPU 급상승 구간을 보이는 monitor.sh 로그
      - WATCHDOG, SIGTERM 종료 로그
      - CPU_MAX_OCCUPY 변경 전후의 생존 시간/종료 여부 비교

  3. Deadlock
      - ps -ef에서 PID가 계속 존재하는 증거
      - top -H 또는 ps -L에서 스레드별 CPU 사용이 정체된 증거
      - 메모리 사용량과 로그 진행이 특정 시점 이후 멈춘 증거
      - 마지막 WAITING/BLOCKED 로그를 이용한 락 순환 대기 추론
      - MULTI_THREAD_ENABLE=true/false 비교

  - 언제 측정했는가: timestamp
  - 어떤 프로세스인가: pid
  - 실행 중인가, 대기 중인가: state
  - CPU를 얼마나 쓰는가: %CPU
  - 실제 물리 메모리를 얼마나 점유하는가: RSS
  - 스레드가 몇 개인가: threads
